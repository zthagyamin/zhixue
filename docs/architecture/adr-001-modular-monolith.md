# ADR-001：保留部署形态，改为受约束的模块化单体

- 日期：2026-09-17
- 状态：本次工程采用；后续模块迁移仍按各工作包验收
- 范围：网站/Companion 代码边界、开发规范；不改变成绩/内容协议

## 背景

项目已有来源、内容版本、学习插件、每日与长线计划、论文、账号同步及不可变学习事件。主要风险来自巨型控制器和不同入口分别重建同一规则。真实缺陷包括评分参考形态不一致及安装清单遗漏。已有测试、数据和旧客户端使全量重写风险很高。

## 比较

| 方案 | 收益 | 成本与风险 | 结论 |
| --- | --- | --- | --- |
| 只拆页面文件 | 较快改善可读性 | 依赖与状态所有权不变，仍向大控制器集中 | 不足以解决当前问题 |
| 分层模块化单体、逐条行为迁移 | 保留现有部署/数据/回归；新逻辑有真实边界 | 迁移期保留兼容入口，需要自动门禁 | 采用 |
| 新框架或微服务重写 | 可重新组织一切 | 重复实现兼容、分布式状态和发布成本，难以证明与旧记录等价 | 当前不采用 |

## 决策

先隔离纯内容/评价/数学领域，类型契约不再由 UI 注册器拥有。之后将学习/计划/同步用例拆至应用层，用 ports 注入 I/O，界面只订阅显式状态。部署单元和存储保持现状。Python 维护同版规则与跨语言夹具，暂不尝试在浏览器运行 Python 后端。

保留旧模块路径的兼容导出，禁止复制规则实现。统一 Companion 程序清单；打包和安装从同一清单读取，并校验相对路径及保护范围。

使用实际静态依赖图防止新反向依赖、包/平台依赖和循环；对遗留热点做行数、字节和导入数量上限。此门禁不能证明语义正确，也不能取代行为、安全和实际安装验证。

## 后果

增加有限的公开入口与兼容文件，但旧调用行为保持。开发者需明确逻辑属于规则、用例、I/O 还是视图。既有热点有小修需求时，优先抽取而不是扩大预算；确需例外另写 ADR，说明边界和退出条件。

## 检查

- 领域核心能在 Node 单独运行，不导入 React/页面/数据库；相关 Python 规则使用共同输入预期。
- 新能力依赖公开模块接口，接口反向依赖由检查器阻断。
- 原始内容、正式事件、FSRS 与用户资料不因目录迁移改变。
- 安装/升级/失败回滚仍由实际测试证明。
- 线上发布必须另有实际源码与部署证据。
