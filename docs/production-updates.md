# 上线后的更新流程

1. 先保留开发仓库现有工作；确认本次范围，检查数据结构是否向后兼容。当前浏览器数据库版本不变；不得借更新清理用户记录。破坏性服务契约与数据库迁移必须单独设计、备份和验证。
2. 更新网页和 Companion 版本、CHANGELOG、版本说明及用户可见的 `/updates`。重新生成安装包；运行 `npm test`。涉及 Companion 行为时补充对应 Python 回归。
3. 验收桌面和手机页面、实际更新提醒、失败重试、诊断报告复制。学习路径检查保存、同步和回写各层，不能把 HTTP 成功当成学习记录写入成功。
4. 开发提交先保留在 GitHub。Sites 使用独立发布镜像，保留其现有父提交，不把开发仓库完整历史再次推入发布镜像。
5. 在干净开发树和发布树上运行 `node scripts/prepare-sites-snapshot.mjs SOURCE PUBLISHER EXPECTED_PARENT`。该命令只在本地准备候选提交，核对项目、父提交和源码树，输出开发/发布 SHA 映射；不推送、不移动分支。执行前核对远端发布分支仍等于 EXPECTED_PARENT。候选无须移动开发分支。
6. 正常快进推送候选发布提交（不使用 force），成功后将发布工作树快进到该提交。从发布工作树提交 Sites 构建，引用完整发布 SHA。保留版本号、开发 SHA、发布 SHA 和源码 tree 映射。
7. Sites 显示成功后运行 `node scripts/smoke-public-release.mjs https://zhixue-daily.zthagyamin.chatgpt.site VERSION`，再验收登录后的学习功能。冒烟只核对公共页面、版本和匿名重定向，不证明登录、学习或回写成功。

## 失败与回退

发布构建失败时保留当前线上版本和候选提交，记录失败阶段。先定位镜像、构建或部署环节，不重复盲推历史。必要时把上个已验证版本的源码树作为发布分支的新子提交部署；不要重写 GitHub 或发布分支历史。源码回退不等于数据库回退，含数据迁移的版本不可套用纯代码回退。

## 用户反馈

暂未设置公开反馈地址。报告只能由用户预览、复制并自行提供，不自动发送。报告不核验保存与同步状态，不记录原始错误、笔记内容、作答、完整浏览器标识、文件路径、登录凭据或地址参数。
